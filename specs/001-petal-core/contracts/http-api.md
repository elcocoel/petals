# Contract: HTTP API and MCP

**Version**: api/v1 | **Owners**: W4 (tool routes, MCP), W5 (agent routes) | **Consumers**: web (W6), skill, CLI and IronClaw package (W7), any agent, judges

One Hono app, `petalApp(cfg)` from `@petal/agent`, made of two parts:

- **Tool routes**: `httpApp(ctx)` from `@petal/tools`. Every tool in [tools.md](./tools.md) has one route; bodies and responses are the tool's input and output. Also `/api/v1/health` and `/mcp`.
- **Agent routes**: `agentRoutes(...)` from `@petal/agent`: chat, runs and attestation reports. They live with the agent because the agent imports the tools; one-way dependencies, no cycle.
- **Auth routes**: from `@petal/agent`: sign-in, the session and invites ([below](#sign-in-sessions-and-invites)). Mounted before the tool routes, so their open CORS doesn't answer for them.

Locally `pnpm api` (or `petal api`) runs `petalApp` under Node on `http://localhost:8787`. On a host it is mounted in the web app at `/api/[[...route]]` with `@hono/vercel`. The HTTP API is the base door; the skill, the CLI, MCP and the IronClaw package sit beside it over the same tools ([packages.md](./packages.md#the-five-doors)).

## Rules

- JSON in and out, UTF-8. `tools_version` in every response.
- No account, key or payment is needed for anything except publishing and Petal's own agent (FR-030, SYS-051).
- CORS: open on the tool and agent routes, so agents and other sites can call them, with no `Access-Control-Allow-Credentials`, so a browser never sends a session across origins. The auth routes, `/api/v1/me` and `/api/v1/explorations` send no CORS headers.
- Rate limits per address (in memory in Phase A): 60 tool calls per minute; 10 new agent chats per hour, plus 60 follow-ups per hour on an existing run. A person spending their own credit isn't held to the 10 new chats (T374): the follow-ups still count. Over the limit: `429` with `{ error: { code: "rate_limited", retry_after_s } }`. An address is `cf-connecting-ip`, else the socket on a local deployment, and on a public one everyone without it shares a limit. `x-forwarded-for` and `x-real-ip` never count. An IPv6 address counts as its /64.
- A body is at most 256 KiB, a chat 512 KiB, and a posted reading 2 MiB on the wire and 32 MiB inflated: `400 bad_input`. `/mcp` takes one call per POST, so a batch is `400 bad_input`.
- Global limits (T300, `.env.example`). Daily caps answer `429 rate_limited` with `retry_after_s` until midnight UTC. A fresh read past its turn, two at a time, answers the same with a short `retry_after_s`, and one that takes too long answers `502 source_failed`. Past the data budget, a write a stranger can cause answers `429 budget_exhausted`.
- Errors: HTTP status from the error code (`bad_input` 400, `unauthorised` 401, `invite_required` 403, `not_found` 404, `cannot_read` 422, `invalid_spec` 422, `rate_limited` 429, `budget_exhausted` 429, `payment_required` 402, `not_on_this_site` 403, `source_failed` 503, `internal` 500), body `{ error: { code, message, hint } }`. `source_failed` is 503, not 502, because Cloudflare, in front of the live server, swaps an origin's 502 or 504 for its own page, and the person would read that instead of the message.
- Long tools (`get_snapshot` on a live pull) accept `Accept: text/event-stream` and then stream `progress` events before the final `result` event.

## Agent chat (SSE)

`POST /api/v1/agent/chat`, body `{ "messages": [{ "role": "user" | "assistant", "content": string }], "draft"?: { "spec"?, "entry"? }, "run_id"?: string }`, response `text/event-stream`. With `run_id`, the chat continues a stored run (its messages and draft are loaded).

**Runs you can leave and come back to.** Every chat is a run, stored by `RunStore` (`.petal/private.db`), and a job in the one server process. The SSE stream only observes it, so a viewer coming or going changes nothing. `GET /api/v1/agent/runs/:id` returns it, finished or not.

**Reconnecting.** Each stored event has a place in the run's log, its `seq`: 0, 1, 2…, across all the chats of the run. An event's SSE `id` is its `seq`. `Last-Event-ID: <n>` starts after `n`; `?from=<n>` starts at `n`; if both are sent the header wins. A heartbeat carries no `id`, and isn't stored. A chat's own stream starts at the chat's first event, so its `id`s carry on from the run's earlier chats. A run's stream ends when the run does; a stream that ends without `done` or an `error` says nothing about how the run ended, so read the run.

**Stop.** `POST /api/v1/agent/runs/:id/stop` aborts the model call and the tool in progress, settles the budget for what was used, and answers once the run has ended. It reports what it witnessed: `{ status: "stopped", stopped: true, already_finished: false }`, or `{ status: <how it ended>, stopped: false, already_finished: true }` for a run that had already finished. If neither can be said (`status: "running"`, no job holds it), both are false. Whoever holds a run's id may stop it, as they may continue it. Budget for an aborted call counts only what it is known to have cost.

**A restart.** No run is resumed: that would spend money with nobody watching. On boot, every run still `running` gets an `error` event with code `interrupted` and that status, no `done` follows it, and every hold on the ledger is released. Holds lost this way aren't counted as spent, because what those calls cost can't be known. A process that only builds the app (a test, a check) leaves alone the runs of a live process that started a chat on the same store. A chat with `run_id` continues a `stopped` or `interrupted` run from its saved thread, which is saved after each model answer and each tool.

**The yes (J4, SYS-054).** On a real model, a new map waits for the person: a fresh read through `get_snapshot`, and `propose_spec` and `render_flower`. A `get_snapshot` with no yes behind it is answered from the newest snapshot stored for that target, or the one its `at` names, however old, unless it asks for `fresh`. It's marked `stored_only`, reaches no source, and approves nothing. `target_key` is the `network`, plus its params in canonical form when it has any. A call goes ahead if its target, its snapshot, or the spec it varies is already approved in this run, including a flower already drawn and a `draft` the person sent. Otherwise it goes ahead if the latest user message tells the agent to draw something by name, even as a first message, unless the target is a candidate of an `ambiguous: true` `find_target`. Or if that message is a yes, the agent has said something before it, and what it last said leaves one thing to agree to: no either-or in its last question, no numbered list. One yes covers one new target. Otherwise the model's tool result is `{ error: { code: "approval_required", message, hint } }` and this event goes out. The rest of the chat keeps the tools that only read, and loses `propose_spec` and `render_flower` unless something is already approved. Asking again for what was refused isn't run, and a model left with no words gets one call with no tools, so it has to speak. A reply naming a candidate by ordinal, chain or address counts for that candidate when the last `find_target` said `ambiguous: true`. What's approved is read back from the run's thread and flowers, so it survives `run_id` and a restart, with no new column. A recorded run isn't held. This is consent, not security: a client can write its own history, and the invite budget is the boundary. `approval_required` has no HTTP status, because it never leaves the loop: the tool routes and MCP are not held (SYS-030).

A conversation's `settings.model` and `settings.effort` are what its chats run on (T370): the catalogue is the allow-list, effort goes only where the model offers it, and a fallback stays inside its promise, so a signed pick never becomes unsigned and a passed-through model with none fails plainly. Limits per chat: 8 tool rounds, 300 s wall time (`PETAL_RUN_MAX_S`), $0.05 on an invite, and `PETAL_PERSON_USD_PER_CHAT`, default $0.50, on a person's own credit. A daily cap (`PETAL_LLM_DAILY_USD`, default 3) protects the one server key; past it, including mid-way through a chat, the agent returns `budget_exhausted` and points to the skill (bring your own agent).

Model calls inside a chat are not streamed, so each one can carry a TEE signature (streamed completions get a weaker gateway signature). Progress comes from Petal's own events instead.

Without `NEAR_AI_API_KEY`, the server answers with a recorded transcript (`recordedClient`) and says so in `done.model = "recorded"`. That keeps the judge path working with no credentials (SC-009).

## Sign-in, sessions and invites

The server reads three settings. `PETAL_API` is the site's public address: the recipient, the allowed Origin and the cookie's name all come from it, never from a request. `PETAL_AGENT_ACCESS` is `gated`, the default and what anything unrecognised means, or `open`. `PETAL_WALLET_KEY` seals wallet addresses, and is 32 bytes as hex or base64. A server that is gated and has a model key refuses to start without it. Elsewhere (`open`, `NODE_ENV` development or test, no model key) a throwaway key is made at the first sign-in, with one warning line, and wallets sealed under it can't be read after a restart.

**A person** is a private id, `prs_<hex>`, with wallets attached. A wallet is a binding, `near:<network>:<account>`: testnet and mainnet are different wallets, so different people, even for the same implicit account. Addresses are stored sealed, with a keyed hash as the unique index.

**Sign-in, NEP-413 only.**

1. `POST /api/v1/auth/challenge`, no body: `{ nonce, message, recipient, expires_at }`. `recipient` is the site's hostname; `message` is a plain sentence naming it; `nonce` is 32 bytes as base64, valid 5 minutes, single use. These go to the wallet as they are.
2. `POST /api/v1/auth/verify`, body `{ "network": "testnet" | "mainnet", "proof": Nep413Proof }`, where a proof is `{ type: "nep413", account_id, public_key, signature, message, nonce, recipient }`. A signature may be base64, base58, or `ed25519:` and base58. The key must be a full-access key of the account, read with `view_access_key` on that network. An implicit account that doesn't exist yet passes when its id is the hex of the signing key, and only while `view_account` says it doesn't exist.
3. On success, in one step: the person is found or created, the wallet bound, an anonymous session's runs and explorations move to them, and a new session replaces the old one, keeping its invite. `{ person_id, network, wallets: [{ caip10, network, account_id, proved_at }], claimed_runs, claimed_explorations }`. A first sign-in reads the same as a returning one.

Refused with `unauthorised` (401): another message, another recipient, a bad signature, a nonce that's unknown, used or expired, a key that isn't a full-access key of the account. NEAR's RPC not answering is `source_failed` (502), and the same proof can be sent again. A person signing in with another wallet changes person; nothing is merged. Linking a second wallet (SYS-023) isn't built yet.

**A session** is an opaque 256-bit value, of which only the hash is stored, with a subject that is a person id or an anonymous handle (`anon_<hex>`). It lasts 30 days from when it's made. The cookie is HttpOnly, SameSite=Lax, Path=/: `__Host-petal_session` and Secure when `PETAL_API` is `https://`, otherwise plain `petal_session`. A session can read and continue its subject's runs and draw on an invite, and can't approve anything irreversible: publishing still takes a signature.

**Origin.** A POST to an auth route, to `/api/v1/agent/chat` on a real model, or to `.../stop` answers `unauthorised` when its `Origin` isn't the site's. On a local site (no `PETAL_API`, or `localhost`, `127.0.0.1`), a local page matching the `Host` it asked is the site. With no `Origin` and no `Sec-Fetch-Site: cross-site` it isn't a browser, and it passes.

**Run owners (SYS-014).** A chat on a real model creates its run with the session's subject as owner, opening an anonymous session if there is none. Once a run has an owner, only that owner may read, follow, continue or stop it. To anyone else it answers exactly as a run that never existed: `404 { error: { code: "not_found", message: "no run <id>" } }`. The owner never appears in a run. A recorded run opens no session and has no owner; it and any run older than owners stay open to whoever holds the link, and continuing one leaves it unowned. There is no way back to an anonymous session's work once its cookie is lost.

**Who pays (SYS-050 to SYS-052).** With `agent_access: "gated"`, a chat on a real model needs a person with credit of their own or a session holding an active invite. A person's credit (T374) belongs to the person, so any of their wallets and any browser reach it, it comes before an invite the session holds, and it stops a chat at `PETAL_PERSON_USD_PER_CHAT`, default $0.50. The daily cap doesn't hold it (Elco, 9 Nov: the cap is for unpaid spend only). On a public site, its runs read the chain, pages and search from the server (Elco, 9 Nov), while the site's own doors still read nothing. When it ends, the chat's stream carries `error` with `payment_required`, and the next chat answers `402` with the same message unless the session holds an invite. A signed-in person with no credit and no invite gets `402 payment_required` too (9 Nov): they pay for Petals' agent in NEAR, below. The rest of this section is about invites, whose caps don't change. Without one it spends nothing, stores nothing, and answers `403 { error: { code: "invite_required", message, hint } }`, with `hint` pointing to `/connect`. The recorded demo, reading a run, and every tool need no session. `open` is for an operator's own tool: no invite is asked for, and the daily cap still applies.

**A person's agents, across their projects (9 Nov, `coordinator/agent-house-test.md`).** The person copies one prompt into whichever agents they want; it carries an agent link, which can only wait for jobs. The work itself goes through each job's project, on a continue link.
- `POST /api/v1/agents/link` (signed in, same-origin) → `{ id, token, created_at }`: the token, `petal_agent_…`, is shown once and only its hash is kept. A new link leaves the older ones working. `GET /api/v1/agents/link` → `{ links: [{ id, created_at }] }`; `POST /api/v1/agents/link/revoke { id? }` revokes one, or all.
- `POST /api/v1/agents/wait`, `Authorization: Bearer <token>`, `{ as, worker?, wait_s?, can? }`: `can` is what this worker says it can do, in its own words, such as whether it splits work among sub-agents and on which models (Elco's swarm lean 2, 11 Nov; migration 26), kept with the worker, the latest wait's winning and null when it says nothing. It waits for an open job sent to `as` (case ignored), or else to anyone, in any of the person's projects, and takes it, only while the request is still open. → `{ job: { id, kind, title, brief, inputs, to }, project: { exploration: <a continue link url>, question }, view }`, or `{ job: null }`. `view` is the person's view (`view/v1`, theirs or the default): their agent passes it to `render_flower`, so every flower it draws is drawn as they see it (one-source.md; `take_job` gives it too). It answers by `wait_s` (default 50) and never later than 90 s, because the tunnel in front of the site closes a request idle for 100 s; the agent's own command asks again. A wait that's open right now is the agent's presence.
- `worker` (10 Nov, swarm.md step 1; migration 20) is the window or sub-agent asking: 1 to 32 letters, digits, `-` or `_`, made by `petal.mjs` when it joins. Several workers of one name each take their own job. Without it, a wait is as before.
- `GET /api/v1/agents` (signed in) → `{ agents: [{ name, n, worker, waiting, last_seen, can, job: { id, title, exploration } | null }] }`, `can` what that worker says it can do, or what the agent said through a connector's `take_job`, or null: one entry per worker, each agent's in the order they first came. `name` is the agent's, for `disconnect`; `n` is the worker's place, 1 for the first, so the page reads them "Codex", "Codex 2" (it names agents: `readableAgent`). An agent that never waited as a worker is one entry, with `worker: null` and `n: 1`. Disconnecting an agent takes all its workers, and connecting it again starts from its first.
- `hand_job` takes `to` (an agent's name); a job and its event carry `to` and `taken_by`. A run's system message lists who's connected.
- **A conversation per job** (10 Nov, swarm.md step 2; migration 22). `hand_job` gives each job its own conversation: an exploration of the person's, in the handing conversation's folder, titled by the job, with the brief as its question. A job and its event carry `conversation`. Its worker works there: `jobs wait`, `take_job` with the agent key, and `take_job` with the project's link (which now answers `link`) hand out a continue link for it. `GET /api/v1/conversations` lists it like any other door's work. `report_job` takes either conversation's link, and its summary (or why it failed) lands in the job's own conversation as a note, as well as in the conversation that handed it out. `GET /api/v1/explorations/:ref` there shows `presence: { client, n, … }`: the agent's name and which of its workers. `list_jobs` (`GET /api/v1/explorations/:ref/jobs`) gives each job's `conversation` and `n`, the place of the worker that took it (1, 2, …, as `GET /api/v1/agents` counts them). An older job, with no conversation, works in its project as before.
- **Supervision, without timers** (11 Nov, swarm.md step 3; migration 23). Each take of a job with its own conversation hands its worker a continue link, which the job remembers. Every call through it marks the job alive: `last_seen` in `list_jobs`, from which the page says it's quiet. `POST /api/v1/jobs/:job/stop` (signed in, one of theirs) stops an open or taken job. `POST /api/v1/jobs/:job/retry` puts a taken, failed or stopped one back as open, for whoever takes it first, and `POST /api/v1/jobs/:job/hand-over { to }` does the same for one of their connected agents. Waiting agents wake. Petals' agent does the same with `retry_job { job, to? }`, and its job notes say who holds each taken job and when it was last seen. Once a job is stopped or sent again, its old worker's next call through that link is refused, `unauthorised` with `error.ended` `stopped` or `handed_over`, telling it to report nothing and wait for the next one. → `{ job: { id, status, to, taken_by, conversation, updated_at } }`; 404 for anyone else's job, 400 for one in the wrong state.
- **A job in parts** (11 Nov, swarm.md step 4; migration 24). `hand_job` takes `parts: [{ title, brief, inputs?, to? }]`, two or more. Each part is a job of its own, for any worker, and all share `part_of` and one conversation, titled by the job. The run emits a `job` event per part, and `list_jobs` and the events carry `part_of`. When the last part reports, Petals' agent takes them all up at once, as one turn (`(Petals) All N parts of the job came back…`), and only the report that completes the group starts it. Its job notes number each part ("part 2 of 4").
- **Managing jobs from the chat** (11 Nov, Elco's swarm leans 2 to 4). Petals' agent has `stop_job { job }`, by the person's stop rule: an open or taken job of its own conversation stops, and its worker hears `ended: stopped` on its next call. The system message's "Agents connected" gives each agent's `can`, its own words, as data. `hand_job`'s parts are for sending work to different agents; one agent alone, or one that says it runs sub-agents, gets the whole job and splits it itself. `take_job` with `agent_key` takes `can` too, kept as the agent's own.
- When a report lands (`report_job`), Petals' agent takes it up at once: a new turn in the run that handed the job out, with a user message starting `(Petals) The job "…" came back from …`, paid from the person's own credit. With none, or the run already going, the report waits for the person's next message. The conversation's live signal fires, so a page that follows it reads the run again.

**Paying in NEAR (9 Nov; `specs/003-target/proposal-payment.md`).** A signed-in person adds to their own credit with one plain NEAR transfer from their wallet to Petals' account. The server holds no key; it reads the transaction back from the chain. A public site counts mainnet NEAR only, since testnet NEAR is free and NEAR AI bills real dollars; a site that isn't public (a lane, the journey server) takes testnet too, so the step can be walked for nothing.
- `GET /api/v1/pay` → `{ network, receiver, near_usd }`: the network the person signed in on (mainnet for anyone else), where to send NEAR (`petals.near`, or `petals.testnet`), and dollars per NEAR now from NEAR Intents' token list (`null` when it can't be read).
- `POST /api/v1/pay { network, account_id, tx_hash }`, same-origin, signed in. The server asks NEAR's RPC for the transaction's FINAL outcome, sent by `account_id`, which must be one of the person's wallets on that network. A successful transaction whose Transfer actions send NEAR to the receiver goes onto the person's credit, in dollars at `near_usd` now, under its hash, so it counts once however often it's sent. → `{ added_usd, added_near, near_usd, credit: { funded_usd, spent_usd, left_usd, usd_per_chat } }`, with `added_usd: 0` the second time. Refusals: `401 unauthorised` (not signed in, or not their wallet), `404 not_found` (NEAR has no such transaction), `400 bad_input` (not a successful NEAR transfer to the receiver, or the wrong network), `502 source_failed` (the chain or the price couldn't be read; nothing changed).

**A top-up through NEAR Intents (10 Nov; Elco: "let users pay with anything from anywhere").** Mainnet, as NEAR Intents is, from any token on any chain its 1Click lists, with one plain transfer from whatever wallet the person has and no key given to anyone.
- `GET /api/v1/pay/tokens` → `{ tokens: [{ asset, chain, symbol, decimals, usd }] }`: what a person can pay from, as 1Click lists it.
- `POST /api/v1/pay/intents { usd, origin_asset, refund_to }`, same-origin, signed in → `{ top_up: { deposit_address, deposit_memo, origin_asset, amount_in, amount_in_formatted, amount_in_usd, amount_out, amount_out_usd, deadline, usd, status } }`: a real 1Click quote, EXACT_OUTPUT, for `usd` dollars of USDC delivered into NEAR Intents under petals.near; the person sends `amount_in` of their token to `deposit_address` before `deadline`, and anything 1Click can't swap goes back to `refund_to`. 1Click adds 0.25% without a partner key. `400` for an amount over $1,000 or under $0, `502` when 1Click can't quote it.
- `GET /api/v1/pay/intents/:deposit_address` → `{ top_up: { deposit_address, status, credited_usd, origin_tx, destination_tx }, credit }`, theirs only: where the swap stands (1Click's own status: PENDING_DEPOSIT, KNOWN_DEPOSIT_TX, PROCESSING, SUCCESS, INCOMPLETE_DEPOSIT, REFUNDED, FAILED). At SUCCESS the dollars it delivered go onto their credit, once, as their own entry, at the price they came in at, and Petals' top-up fee if that switch is on (price/v1).

**Invites.** `scripts/mint-invite.ts <usd> [days]` makes one, for 14 days unless told otherwise, and prints its token once; only a hash of the token is stored. `--revoke <id>` ends it. `POST /api/v1/auth/invite`, body `{ token }`, puts it in this session, opening an anonymous one if needed. Several sessions can redeem one token, and they draw on one budget. `{ invite: { status: "active" | "spent" | "revoked" | "expired", budget_usd, spent_usd, left_usd, expires_at } }`. A token that is unknown, revoked or expired answers `unauthorised`; a spent one `budget_exhausted`.

Each model call of a chat reserves against the invite and the daily cap, then settles both, so the last call can pass the budget by what it costs. When the budget ends, the chat's stream carries `error` with `budget_exhausted` and a plain message, then `done`, and the next chat answers `429` with the same message before any model call. An invite revoked or expired mid-chat stops at the next call the same way, and the next chat answers `403 invite_required`. A restart gives back every hold on an invite.

**402 from NEAR AI.** `budget_exhausted` with a plain message for each kind: `api_key_limit_exceeded` (the key's own lifetime limit), `insufficient_credits`, `no_credits`, `no_limit_configured` (the sponsor account) and any other (unknown). None is retried on another model, and the figures in NEAR AI's message stay out of the event.

## Explorations and links

The tools are in [tools.md](./tools.md#explorations-m-system-t194-additive-still-toolsv1); these routes add a session. They read the cookie, so they send no CORS headers, `Cache-Control: no-store`, and a POST from another site answers `unauthorised`. To anyone without access an exploration answers `404`, one body whatever the reason.

A link is 32 random bytes in base64url, and only its hash is stored. Making, listing and revoking links takes the owner's session, an anonymous one included, and never a link. An exploration moves with its anonymous session at sign-in. A site's run makes one at its first flower, and each new flower is a step, door `site`.

**In the web app:** `apps/web/app/d/[hash]/route.ts` and `apps/web/app/s/[token]/route.ts` are route handlers with no page, which pass to this app as `/mcp`'s does.

- **Kept**: sign-in (its one RPC check of the signing key is the site's own job), `/api/v1/me`, the workspace, explorations and links, `/d`, `/s`, `GET snapshots/:sha256` and `describe`, `figures`, `specs/propose` and `validate`, `render`, `networks`, `relations`, `health`, `/skill.md`.
- **Health** says `agent_access: "none"`, `llm: "none"`, `map: "held"` and `public: true`. The model key is never loaded.
- **`PUT /api/v1/explorations/:ref/snapshots/:sha256`** (both modes): a reading made on the person's own machine, so the site can draw it. The owner or a continue link; the body is the snapshot JSON, `Content-Encoding: gzip` allowed. The name must be the sha256 of its canonical JSON and the body a valid snapshot, or `400 bad_input`; anyone else gets the same `404` as nothing at all. Answers `{ exploration, sha256, stored, origin }`: `stored` is false when the site already held it, which changes nothing, and `origin` is `their_machine` for a posted reading, which this site never reads again, or `this_site`. Then it serves at `GET /api/v1/snapshots/:sha256`, and `save_step` with the spec inline checks against it. At most `PETAL_POSTED_SNAPSHOTS_PER_DAY` (200) new ones a day, and none past the data budget.

## Contract tests (W4 tool routes, W5 agent routes)

- Every tool route returns what its tool returns for the same input (fixture snapshot, fake map).
- SSE: a recorded agent run produces the event order `run → stage → tool_call → tool_result … → flower → signature → done`.
- Runs: after the client disconnects mid-run, `GET /api/v1/agent/runs/:id` later returns the finished run and its flower. A viewer reconnecting by cursor sees every event once. Stop and a restart end a run as `stopped` and `interrupted`, with nothing held on the ledger.
- Attestations: a stored report is served byte for byte, and its SHA-256 matches `report_sha256`.
- MCP: `tools/list` names and schemas equal the registry; one `tools/call` per tool matches the HTTP result.
